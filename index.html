MÓDULO 01 · HISTORIA Y RECORRIDO

Historia de la IA: de neuronas lógicas a sistemas de IA agéntica.

Hitos y continuidades: reglas, aprendizaje, LLM y sistemas compuestos.

Nota de estudio

Objetivo ampliado: reconocer continuidades entre reglas, aprendizaje y modelos de lenguaje; distinguir hitos de promesas; y situar los sistemas actuales como integración de componentes. Esta cronología no busca un “primer paper” universal: ayuda a evaluar anuncios actuales con evidencia, condiciones y límites. La herramienta propone; la persona conserva criterio y responsabilidad.

MÓDULO 02 · FUNDAMENTOS

Comprender IA evita confundir una interfaz con inteligencia.

Objetivos: distinguir IA, ML, aprendizaje profundo, IA generativa y LLM; reconocer límites; iniciar el ejemplo continuo de un cuestionario Python.

Una pregunta precisa es el primer control de calidad.

No hace falta programar para empezar; sí conviene separar hecho, instrucción, ejemplo y resultado esperado.

Objetivo: practicar listas en Python
Evidencia: 3 preguntas respondidas y explicadas
Autochequeo: ¿qué falta?

Respuesta: criterios para decidir si una respuesta es correcta, no solo una petición amplia.

La IA reúne técnicas para realizar tareas asociadas al razonamiento o la percepción.

No es una sola tecnología ni garantiza comprensión humana. Puede clasificar, predecir, buscar, traducir o generar según su diseño.

ANI es real; AGI y ASI son categorías hipotéticas, no capacidades demostradas universales.

La IA estrecha se optimiza para dominios delimitados. “AGI” y “ASI” describen ideas de alcance general o superior y requieren cautela.

Autochequeo: ¿un chatbot actual es AGI?

Respuesta: no se sigue de que converse bien; una demostración localizada no prueba capacidad general autónoma.

ML aprende patrones; deep learning usa redes con capas; la IA generativa y los LLM son aplicaciones especializadas.

Un LLM es un tipo de modelo generativo de lenguaje; no toda IA generativa es un LLM y no todo ML es deep learning.

El aprendizaje automático ajusta un modelo a patrones observados.

En el cuestionario, un sistema podría estimar qué ejercicio proponer según errores previos; eso no equivale a saber por qué aprende cada estudiante.

La IA generativa produce nuevas secuencias condicionadas por una entrada.

Texto, código, imagen o audio pueden ser salidas. Generar una pregunta Python plausible no demuestra que su solución sea correcta.

MÓDULO 03 · LLM

Un LLM predice continuaciones de tokens dentro de un contexto finito.

Objetivos: explicar token, entrenamiento, inferencia, contexto y alucinación; diseñar revisión para el cuestionario Python.

Los tokens son unidades que el modelo procesa, no siempre palabras completas.

Una solicitud se fragmenta, se representa y se usa para estimar la siguiente unidad. Esto explica por qué longitud y redacción importan.

El entrenamiento ajusta parámetros con datos; la inferencia usa esos parámetros.

Pedir un ejercicio es inferencia, no una actualización inmediata de los pesos del modelo.

El contexto limita qué información puede considerar una respuesta en una interacción.

Nivel: principiante
Tema: listas
Pide: pregunta, solución y explicación breve

Un contexto largo tampoco garantiza que cada detalle sea seguido perfectamente.

Una alucinación es una salida plausible que no está respaldada de forma fiable.

Los LLM pueden errar hechos, código, citas o cálculos. Verifique fuentes, ejecute pruebas y no delegue decisiones de alto impacto sin controles.

Autochequeo: ¿respuesta fluida = respuesta cierta?

Respuesta: no; la fluidez lingüística no es evidencia independiente.

MÓDULO 04 · AGENTES

Un agente combina modelo, estado, herramientas y una política de ejecución.

Objetivos: separar workflow y agente; entender harness, skills, MCP y orquestación con límites claros.

Un workflow fija pasos; un agente decide próximos pasos dentro de límites definidos.

El harness encuadra al modelo con contexto, herramientas y guardas.

“Hardness” aquí se interpreta como harness: no es una capacidad mágica, sino diseño de límites, permisos y retroalimentación.

Autochequeo: ¿el harness concede permisos?

Respuesta: no por sí mismo; los permisos deben ser definidos y aplicados por el sistema.

Una skill aporta instrucciones y procedimientos reutilizables para una tarea delimitada.

Una skill de revisión puede exigir ejecutar el quiz, explicar errores y citar fuentes. No reemplaza juicio ni autorización humana.

MCP estandariza cómo un cliente descubre y usa capacidades externas; no concede permisos.

El protocolo no convierte una herramienta en segura: identidad, autorización, validación y alcance siguen siendo responsabilidades del sistema.

Consultar documentación de MCP

Un orquestador coordina tareas, estado y evidencia entre componentes.

En el quiz: generar borrador → ejecutar ejemplos → pedir revisión → presentar evidencia. Más componentes aumentan coordinación y superficie de fallo.

MÓDULO 05 · MÉTODOS

SDD, ODD y RDD tienen propósitos distintos para convertir intención en evidencia revisable.

Objetivos: especificar el quiz Python, administrar incertidumbre y obtener evidencia independiente sin confundir estos métodos con una secuencia universal.

SDD significa Spec-Driven Development: empezar con una especificación y criterios de aceptación verificables.

Especificación: quiz de listas para principiantes
Aceptación: 3 preguntas; soluciones ejecutables;
explica cada error frecuente.

Su propósito es reducir ambigüedad antes de implementar.

ODD significa Organic Driven Development: adapta el esfuerzo al riesgo y a la incertidumbre.

Leer documentación ODD/RDD de Gentle AI

RDD significa Receipt-Driven Development: exige evidencia independiente sobre un candidato congelado.

Una revisión externa o evidencia independiente evalúa un candidato sin cambiarlo. RDD no sustituye pruebas ni autoriza entrega, publicación o despliegue.

Autochequeo: ¿una revisión RDD permite publicar?

Respuesta: no; la autorización de entrega es una decisión separada.

MÓDULO 06 · ECOSISTEMA

El ecosistema coordina prácticas, no transfiere responsabilidad al modelo.

Objetivos: ubicar Gentle AI, Gentle Shell y Engram sin inventar comandos, versiones o capacidades.

El capítulo “De Token a Agente” conecta modelo, contexto, harness, conocimiento y patrones.

Esta explicación original toma ese recorrido como lectura complementaria: modelo → inferencia → presupuesto de contexto → harness → conocimiento (skills y memoria) → patrones → proceso. El capítulo no se atribuye ODD ni RDD.

Leer “De Token a Agente”

Gentle AI documenta prácticas de desarrollo guiado, incluida la convención ODD/RDD.

Use la documentación oficial como fuente de convenciones. La rama principal puede contener cambios no publicados; compruebe el contexto antes de adoptar una práctica.

Gentle Shell se describe públicamente como un shell de desarrollo controlado, nativo de Pi.

Su papel es encuadrar el trabajo de desarrollo; esta presentación no inventa comandos ni asume una versión instalada.

Abrir README de Gentle Shell

Engram se describe públicamente como memoria persistente agnóstica al agente, distinta de los pesos del modelo.

Guardar memoria requiere criterios de privacidad, vigencia y procedencia.

Abrir README de Engram

El criterio final es una cadena de evidencia, no una respuesta impresionante.

Para el quiz Python: defina aceptación, genere un borrador, ejecute el código, explique resultados, revise de forma independiente y decida explícitamente qué entregar.

Chequeo final

¿Qué harás primero? Escribir un objetivo verificable y una condición de aceptación antes de pedir generación.
